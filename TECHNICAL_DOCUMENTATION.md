# Техническая документация

## 1. Общие сведения

### 1.1. Наименование системы

`ИнфоМед` — информационная система медицинского центра, предназначенная для автоматизации работы регистратуры, врачей, пациентов и администратора.

### 1.2. Назначение системы

Система предназначена для цифровизации ключевых процессов медицинского центра:

- регистрации и аутентификации пользователей;
- ведения карточек пациентов;
- ведения карточек врачей;
- управления справочниками специальностей и медицинских услуг;
- формирования расписания врачей;
- записи пациентов на приём;
- ведения медицинских записей по итогам приёма;
- просмотра истории посещений;
- формирования аналитики и отчётности;
- разграничения доступа по ролям.

### 1.3. Формат проекта

Проект реализован в виде full-stack модульного монолита и состоит из двух приложений:

- `backend` — серверное приложение на NestJS;
- `frontend` — клиентское приложение на React.

Такой формат выбран как оптимальный для учебного, дипломного или демонстрационного проекта: он обеспечивает хорошую управляемость кода, прозрачную архитектуру и удобство локального запуска.

## 3. Общая архитектура системы

Система реализована по клиент-серверной модели.

### 3.1. Логическая схема взаимодействия

```text
Пользователь
  -> Frontend (React, TypeScript, Tailwind)
  -> REST API (NestJS)
  -> Prisma ORM
  -> SQLite
```

### 3.2. Архитектурные принципы

- backend разделён на доменные модули;
- frontend разделён на страницы, layout, формы, API-клиенты, store и UI-компоненты;
- контроль доступа выполняется как на уровне guard’ов, так и на уровне бизнес-логики сервисов;
- сервер использует единый формат ответов;
- валидация входных данных выполняется на уровне DTO;
- маршрутизация и отображение интерфейса зависят от роли пользователя;
- локальный запуск не требует отдельной СУБД PostgreSQL и разворачивается на SQLite.

## 5. Архитектура backend

### 5.1. Точка входа

Точкой входа backend-приложения является файл `backend/src/main.ts`.

При запуске приложение:

- создаёт экземпляр NestJS;
- подготавливает каталог `uploads`;
- публикует статические файлы по пути `/uploads`;
- включает CORS для frontend-приложения;
- подключает глобальную валидацию через `ValidationPipe`;
- генерирует Swagger-документацию по адресу `/api/docs`;
- запускает HTTP-сервер на порту из `.env`.

### 5.2. Корневой модуль

Корневой модуль расположен в `backend/src/app.module.ts`.

Он подключает:

- `ConfigModule`
- `DatabaseModule`
- `AuthModule`
- `UsersModule`
- `PatientsModule`
- `DoctorsModule`
- `SpecializationsModule`
- `ServicesModule`
- `AppointmentsModule`
- `SchedulesModule`
- `MedicalRecordsModule`
- `ReportsModule`

Кроме того, глобально регистрируются:

- `JwtAuthGuard`
- `RolesGuard`
- `ResponseInterceptor`
- `AllExceptionsFilter`

### 5.3. Работа с базой данных

Доступ к базе данных реализован через `PrismaService` в `backend/src/database/prisma.service.ts`.

Назначение сервиса:

- инициализация соединения с базой при старте модуля;
- предоставление общего ORM-клиента всем сервисам;
- обеспечение корректного завершения приложения.

## 8. Валидация, ошибки и формат ответов

### 8.1. Валидация DTO

Глобальная валидация подключена в `main.ts`.

Используются параметры:

- `whitelist: true`
- `transform: true`
- `forbidNonWhitelisted: true`
- `enableImplicitConversion: true`

Это означает:

- принимаются только поля, описанные в DTO;
- примитивы из query и body автоматически приводятся к нужным типам;
- лишние поля отклоняются;
- некорректные запросы отбрасываются до выполнения бизнес-логики.

### 8.2. Преобразование сообщений об ошибках

Backend преобразует ошибки class-validator в понятные сообщения на русском языке с подстановкой читаемых названий полей.

### 8.3. Формат успешного ответа

Через глобальный `ResponseInterceptor` все успешные ответы приводятся к единой форме:

```json
{
  "success": true,
  "message": "Запрос выполнен успешно",
  "data": {},
  "path": "/example",
  "timestamp": "2026-05-13T12:00:00.000Z"
}
```

### 8.4. Обработка ошибок

Все исключения обрабатываются централизованно через глобальный фильтр исключений. Frontend получает нормализованные сообщения об ошибках через функцию `getApiErrorMessage()`.

## 9. Модель безопасности

### 9.1. Аутентификация

- используется JWT-аутентификация;
- access token хранится на frontend в local storage;
- во все защищённые запросы токен передаётся в заголовке `Authorization: Bearer`.

### 9.2. Хранение паролей

- пароли не хранятся в открытом виде;
- используется хеширование через `bcrypt`.

### 9.3. Авторизация

Авторизация реализована на двух уровнях:

- ограничение маршрутов по ролям через `RolesGuard`;
- проверка принадлежности сущностей внутри сервисов.

### 9.4. Политика доступа по ролям

#### Администратор

- полный доступ ко всем доменным сущностям;
- управление пользователями, врачами, услугами, расписаниями, записями и аналитикой.

#### Регистратор

- работа с пациентами и записями;
- просмотр расписаний врачей;
- отсутствие доступа к функциям врача и к полному админскому управлению системой.

#### Врач

- доступ только к своим приёмам;
- доступ только к связанным с его приёмами медицинским записям;
- создание и редактирование записей только по собственным назначениям.

#### Пациент

- доступ только к своему профилю, своим записям и своим медицинским данным;
- создание записи только от собственного имени;
- отмена только собственных записей.

## 10. Архитектура frontend

### 10.1. Слой маршрутизации

Маршрутизация описана в `frontend/src/router/AppRouter.tsx`.

Структура включает:

- публичные маршруты входа и регистрации;
- защищённый layout приложения;
- поддеревья маршрутов по ролям;
- общую страницу профиля врача.

Основные механизмы:

- `ProtectedRoute` проверяет наличие токена и статус инициализации;
- `RoleRoute` проверяет допустимость роли;
- `DashboardRedirect` перенаправляет пользователя на нужный dashboard.

### 10.2. Хранилище авторизации

Состояние авторизации реализовано в `frontend/src/store/authStore.ts`.

Ответственность store:

- хранение `token`;
- хранение `user`;
- хранение флага `initialized`;
- сохранение состояния между перезагрузками через Zustand persist;
- синхронизация JWT в local storage.

### 10.3. API-слой

Клиентские API разделены по доменам:

- `authApi.ts`
- `usersApi.ts`
- `patientsApi.ts`
- `doctorsApi.ts`
- `appointmentsApi.ts`
- `servicesApi.ts`
- `specializationsApi.ts`
- `reportsApi.ts`
- `medicalRecordsApi.ts`
- `schedulesApi.ts`

Общий HTTP-клиент расположен в `frontend/src/api/axios.ts`.

Его функции:

- автоматическая подстановка bearer-токена;
- снятие общей backend-обёртки ответа;
- нормализация сообщений об ошибках;
- построение абсолютного URL к загруженным файлам врачей.

### 10.4. Слой layout

Основные layout-компоненты:

- `AppLayout`
- `Sidebar`
- `Header`

Они отвечают за:

- ролевое боковое меню;
- desktop-режим с фиксированным меню и прокруткой контента;
- mobile-режим с выезжающим меню;
- поиск по разделам;
- уведомления;
- единый каркас dashboard-интерфейса.

### 10.5. Конфигурация навигации

Навигация централизованно описана в `frontend/src/components/layout/navigation.ts`.

Каждый пункт содержит:

- заголовок;
- маршрут;
- иконку;
- описание;
- ключевые слова.

Эта конфигурация используется для:

- построения меню;
- генерации заголовка страницы;
- реализации глобального поиска по разделам.

### 10.6. UI-компоненты

Повторно используемые UI-компоненты находятся в `frontend/src/components/ui`:

- `Button`

## 12. Основные сценарии работы

### 12.1. Регистрация пациента

1. Пользователь открывает страницу регистрации.
2. Frontend отправляет DTO на `/auth/register`.
3. Backend валидирует данные.
4. В транзакции создаются `User` и `Patient`.
5. Пароль хешируется через bcrypt.
6. Генерируется JWT.
7. Frontend сохраняет токен и профиль.
8. Пользователь перенаправляется в личный кабинет пациента.

### 12.2. Вход в систему

1. Пользователь вводит email и пароль.
2. Backend ищет пользователя по email.
3. Выполняется проверка пароля по bcrypt-хешу.
4. Backend возвращает JWT и сериализованный профиль.
5. Frontend сохраняет сессию и открывает защищённую часть приложения.

### 12.3. Запись на приём

1. Пользователь выбирает специальность.
2. Frontend запрашивает врачей и услуги по выбранной специальности.
3. Пользователь выбирает врача и дату.
4. Frontend получает доступные слоты.
5. Backend рассчитывает их на основе расписания врача и уже занятых интервалов.
6. Пользователь выбирает услугу и слот.
7. Backend проверяет права, расписание врача, пересечения врача и пациента.
8. Создаётся запись на приём с автоматически вычисленным `endTime`.

### 12.4. Завершение приёма врачом

1. Врач открывает карточку пациента по `appointmentId`.
2. Врач заполняет жалобы, диагноз, лечение, рекомендации и назначения.
3. Frontend отправляет DTO медицинской записи.
4. Backend проверяет, что врач закреплён за данным приёмом.
5. Backend создаёт `MedicalRecord` в транзакции.
6. Связанный `Appointment` переводится в статус `COMPLETED`.

### 12.5. Формирование отчётов

1. Администратор задаёт диапазон дат.
2. Frontend вызывает endpoints отчётности.
3. Backend агрегирует данные из приёмов, услуг, врачей и пациентов.
4. Frontend отображает карточки показателей и таблицы аналитики.

## 16. Текущие ограничения и технический долг

Текущая реализация пригодна для учебного и локального сценария, но имеет ряд ограничений:

- используется SQLite, а не PostgreSQL;
- даты и время хранятся строками;
- отсутствует refresh token flow;
- используется локальное файловое хранилище, а не объектное;
- отчёты считаются на лету без кэша;
- отсутствует аудит действий;
- часть старых текстовых фрагментов в проекте всё ещё содержит проблемы кодировки и требует отдельной нормализации в UTF-8.
